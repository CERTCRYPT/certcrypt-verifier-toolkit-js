# CHANGELOG

This package follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Entries are one line per change: `type:scope: what changed`, where `type` is
`feature`, `bugfix`, `breaking`, `deprecation`, `security` or `docs`.

## 1.0.0

* feature:Verdict: an artifact set without a base certificate is `INCOMPLETE` under `BASE_CERTIFICATE_PRESENT` and lists `base_certificate` in `required_artifacts_missing`; the target is the one resolved from the supplied artifacts, so Independent-route material with `auto` reports `Independent`. `INPUT_COMBINATION_VALID` covers contradictory sources and strict JSON only
* feature:Verdict: each check fails only with the classifications verifier-toolkit/1 Section 9.7 allows for it, enforced at compile time
* feature:Corpus: `verifyCertifiedFiles(request, files, config)` establishes that a set of files is exactly what a repository publication certificate certifies — the proof verifies as `INDEPENDENT_VALID`, its certificate commits to one `subject.collection/1` of `subject.binary/1` leaves, and the files, byte for byte and in order, reproduce the leaves and the signed root
* feature:Consistency: `verifyConsistency(certificate, snapshots, config?)` evaluates CCVP/1 over the target and snapshot certificates themselves — each verified under the Issued route, each snapshot issuer derived from its signature (`signer.id` plus composite key fingerprint), the namespace named in the target's `payload.context`, timestamps compared as instants, `scope.subject_profiles`, roles and optional `kid` applied. An optional plane: its outcome never changes `verify()`. Held to the `ccvp-consistency` vectors
* security:Subjects: the `subject.ai-decision/1` precondition enforces its closed bounded record, part ids and material nonces unique across one record's input and output, exact salted-commitment part shape, admitted profiles, lowercase MIME essences, valid Gregorian UTC millisecond timestamps, and flat bounded `parameters` and `context` maps
* feature:Independent: capacity evidence is verified before settlement (independence.proof/1 §9, §12.5)
* feature:Material: a `subject.ai-decision/1` subject may deliver disclosed parts in `AiDecisionMaterial.materials`, keyed by the id in the matched record; byte material is canonicalized under the record's profile and matched through its per-part salted commitment, while large binary material may use the verifier-local prehashed path. Unknown ids and prehashed non-binary parts fail closed. Held to `P011` and `V057`
* feature:Verdict: `verify(request, config?)` returns a `VerifierResult` — the verdict, the checks that failed, and the regime that produced it — evaluating whether an artifact reached the conditions associated with `Independent`
* feature:Verdict: Fail-closed throughout; a check that cannot be evaluated never counts as passed, and the 40 checks of verifier-toolkit/1 §9.7 report individually in `failed_check_ids`; the code is chosen as §9.5 fixes it (REJECTED > INCOMPLETE > UNSUPPORTED > ISSUED_INVALID > INDEPENDENT_INVALID), and an Issued verification never reports INDEPENDENT_INVALID
* feature:Issued: `BASE_CERTIFICATE_STRUCTURE_VALID` and `BASE_CERTIFICATE_AUTHENTIC` — structure under the rules and the composite signature, whose post-quantum outcome is also reported in `additional_verifications`; a certificate that fails either is not taken through the Independent route
* feature:Issued: the CCSP/1 envelope is checked in full — closed top level, anchor, issuer signature, signer and composite components; the reserved names; `issued_at` as a real UTC instant with `Z`; `root_id` and digest formats; exactly one issuer signature; `payload.system_id` and `payload.rules_version` against the domain under evaluation (an unknown rules version is UNSUPPORTED); published digests recomputed, a mismatch is REJECTED; `signer.pub_p256_b64` only as SEC1 uncompressed
* feature:Input: strict JSON for every artifact read from a path and for the material of the JSON subject profiles — a member name repeated in any object, at any depth and after escape decoding, rejects the input; repeated array elements are data. `strictJsonParse` is exported for artifacts passed in memory
* feature:Independent: `PROOF_STRUCTURE_VALID` and `PROOF_SIGNATURE_VALID` for the `Proof of Independence` — `proof_id` and `proof_digest` are recomputed, `closure_time` and `consumed_commitment_ids` are mandatory, `independence_result` is exactly `independent`, and the composite signature by the system-domain Level-1 capacity key over the signed view is mandatory under every rules domain
* feature:Independent: the node attestation of a proof (independence.proof/1 §10.15) is authenticated by the proof signature, with no register of nodes, and reported as `attested_node` on `INDEPENDENT_VALID`
* feature:Verdict: no configuration accepts a signature without verifying it; test profiles change which keys and roots are trusted, never whether signatures are verified
* feature:Settlement: `SETTLEMENT_REF_VALID`, `FINALITY_SUFFICIENT` and `COMMITMENT_TTL_VALID` — the settlement reference resolves, the reached finality satisfies the rules (every finality witness of the proof names the profile's substrate and equals the settlement material), and settlement did not occur after the commitment expired
* feature:Capacity: `CAPACITY_EVIDENCE_VALID`, `CAPACITY_BINDING_VALID` and `EFFECTIVE_UNITS_BINDING_VALID` — consumed capacity is evidenced and bound to a `capacity_ref` committed at issuance; the evidence's holder authorization grants exactly the `capacity_commitment_holder` role
* feature:Domain: `SYSTEM_DOMAIN_EXACT` and `CLONE_OR_FORK_REJECTED` — a proof is attributable to this domain or it is not, and a proof that names no `system_id` at all is reported as the foreign context it is rather than as a structural error
* feature:Binding: `LEAF_BINDING_VALID`, `SYSTEM_ROOT_BINDING_VALID` and `ANTI_SPLICING_VALID` — the leaf/subtree hybrid binding, and artifacts from different operations cannot be spliced into one verdict
* feature:Replay: `NON_REPLAY_VALID` — `anti_replay` is recomputed from `settlement_ref` and `subtree_root`; a value bound to another settlement container or leaf fails even when signed
* feature:Foundation: `FOUNDATION_PROFILE_VALID`, `FOUNDATION_SIGNATURE_VALID`, `FOUNDATION_SYSTEM_ID_VALID` and `FOUNDATION_BOOTSTRAP_MATCHES_RULES` — the system foundation the system root is verified against
* feature:Issuer: `ISSUANCE_PARTICIPATION_VALID`
* feature:Material: `ORIGINAL_MATERIAL_COMPARISON_VALID` — an opt-in plane; material not supplied is reported as not performed, never as a failure; material that does not match is ISSUED_INVALID, and material keyed to an index the certificate does not declare is REJECTED
* feature:Presence: `BASE_CERTIFICATE_PRESENT` and `PROOF_PRESENT` — a missing artifact is reported as missing, never inferred from a downstream check that had nothing to evaluate
* feature:Versions: `PROOF_VERSION_SUPPORTED`, `INPUT_MODE_SUPPORTED` and `INPUT_TARGET_SUPPORTED` — an unsupported version or mode is UNSUPPORTED, distinct from REJECTED: the toolkit says "I cannot judge this" rather than "this is invalid"
* feature:Rules: `RULES_DOMAIN_EXACT` — the rules the artifact was issued under must be this domain's
* feature:Foundation: `FOUNDATION_FINGERPRINT_RECOMPUTED` and `FOUNDATION_EQUIVOCATION_DETECTED` — the root is recomputed rather than read, and a foundation signing two different states for the same version is caught. `published_rules_versions` is metadata and gates nothing (system-foundation/1 §6)
* feature:Foundation: the statement and its embedded bootstrap manifest are checked as closed shapes — statement, manifest, entry, quorum, members and `statement_signatures` elements carry exactly their members; `foundation_statement_id`, `statement_issued_at`, `kid`, `member_kid` and `valid_from` have their one format; every P-256 key, the Level-1 key included, is a 65-byte SEC1 uncompressed point
* feature:Foundation: `FOUNDATION_BOOTSTRAP_MATCHES_RULES` also compares the statement's payload digest with `foundation_payload_digest`, so a second statement over the registered root and id is refused even when the quorum signed it; the published profile ships the bootstrap statement and uses it when a request supplies none
* security:Composite: `verifyComposite` enforces the profile's exact layout — `{alg, mode, signatures}`, exactly its two components in order, each with exactly its members, `encoding: "raw-rs-64"` and `low_s: true` — and one encoding per key (P-256 SEC1 uncompressed, Ed25519 raw, ML-DSA-65 1952 bytes), and reports malformed material as such; the required profile is the caller's, never the signature's
* feature:Foundation: `FOUNDATION_SUCCESSOR_QUORUM_VALID` — a successor-binding observation counts only when at least `k` distinct members of its predecessor entry sign its system-manifest/1 §9 payload with verifying composite signatures; non-members, failing signatures and repeated signers never count, and equivocation is established only between observations that passed this check
* security:Capacity: `CAPACITY_BINDING_VALID` compares the burned quantity with `batch_binding_preimage.total_quantity`, the total the batch binding memo anchors, and requires any `batch_manifest.total_quantity` to repeat it. Comparing against the unanchored manifest would let material anchor one total, burn less, and restate the manifest to match the burn
* security:Capacity: `CAPACITY_BINDING_VALID` requires every member `batch_manifest` shares with `batch_binding_preimage` to repeat the anchored value (settlement.aggregated.xrpl/1 §10.1; settlement.binding/1 §6): `total_quantity`, `leaf_count`, `batch_id`, `window_id`, `system_id`, `rules_version` and `settlement_profile_id`. The signed `settlement_ref` binds only the preimage's `batch_id` and `window_id`, so without this a manifest describing a different batch would pass. The shared members are derived from the two types, so a field added to both is compared without being listed by hand
* feature:Settlement: material without `batch_manifest` fails closed as `INCOMPLETE` (`AGGREGATED_INTERPRETATION_UNIQUE`, `batch_manifest` reported missing) before any coherence check reads it
* feature:Settlement: `SETTLEMENT_NOT_RETROACTIVE` — a settlement dated before the commitment it extinguishes is refused
* feature:Capacity: `CAPACITY_NOT_RECONSTRUCTED` — the verifier refuses to reconstruct capacity it was not given, instead of assuming a value that would make the path pass
* feature:Aggregation: `AGGREGATED_INTERPRETATION_UNIQUE` — a batch that admits two readings fails closed instead of picking one
* feature:Input: `INPUT_COMBINATION_VALID` and `TARGET_AUTO_RESOLUTION_VALID` — one source per artifact (a package and separately supplied artifacts are never combined), and `auto` resolves to Independent whenever any Independent artifact is supplied, so evidence without its proof is INCOMPLETE rather than an Issued answer
* feature:Package: `PACKAGE_STRUCTURE_VALID` and `PACKAGE_CONTEXT_COHERENT` — a `verification_package` has the closed member set of verification-package/1 §9.4 (no original material, no foundation, no version or target member) and its `verification_context` and `settlement_reference` agree with the certificate and the proof; both REJECTED otherwise
* feature:Binding: the per-commitment inclusion proof is a closed object of five members with canonical forms, checked before it is folded
* feature:`verifyCollectionElementFromCertificate`: element inclusion from the certificate and one leaf value alone (verifier-toolkit/1 §8.4.2) — the certificate verified under the Issued route, the signed leaves folded to the declared root, every declared leaf profile tried, every position of a repeated value reported
* feature:CLI: `--capacity-evidence`, `--commitment-inclusion-proof` and `--package` beside the per-artifact flags; `--request` is parsed as strict JSON
* feature:CLI: exit codes — `0` for a `*_VALID` verdict, `1` for any other verdict, `2` for a usage error; `--help` / `-h` prints the usage to stdout and exits `0`
* feature:`verifyCollectionInclusion`: Element-level inclusion (`INCLUSION_PROOF_VALID`) against a committed collection root
* feature:`collectionMerkleRoot`: Merkle fold over collection leaves under `COLLECTION_MERKLE_SCHEME`, with `collectionLeafHash` and `collectionNodeHash`
* feature:`digestHexBytes` / `digestHexText` / `digestBytes`: SHA3-256, the digest under every commitment
* feature:Runtimes: Same public surface from `@certcrypt/verifier-toolkit/web` and `/node` (the package root resolves to one or the other by runtime), pinned by `core/public-api.test.ts`, so code written against one runs on the other unchanged
* feature:Cryptography: Composite PQ/T signature verification — ECDSA-P-256 or Ed25519 AND ML-DSA-65 (FIPS 204) over the same domain-separated message, valid only if every declared component verifies
* feature:`initMlDsa65`: Explicit startup initialization for the ML-DSA-65 runtime the composite requires, shipped as an `optionalDependency` so a host that cannot build it still installs; when the runtime is absent the composite fails `UNSUPPORTED` rather than falling back to the classical half alone
* feature:`digestHexStream`: Incremental SHA3-256 for material too large to hold in one buffer; a chunked digest equals a whole-buffer digest, pinned at chunk sizes straddling the 136-byte rate
* feature:`subject.binary/1`: Accept `PrehashedMaterial` — a caller that streamed a file supplies `subject_local_digest_hex` instead of the bytes, for an identical verdict
* feature:`isOpaqueByteProfile`: Decides which profiles may be hashed in chunks, next to the switch that canonicalizes, so a prehashed entry on a canonicalizing profile is `REJECTED` as caller misuse
* feature:`canonicalBytesForSubject`: Canonical bytes per subject profile — binary, text, email, collection, ai-decision and context-snapshot
* feature:`jcsCanonicalizeBytes`: RFC 8785 canonicalization, the signed byte form
* feature:Rules: the production profile carries the corpus commitment of `rules/2026-01`, `17e3a74a4fd05b039da9f740a138c36d353f561d49726c00351843bb518364ff`, the `subtree_root` of its corpus proof (certcrypt-specs `verification/rules/rules-2026-01/`), so `Independent` verification under `rules/2026-01` passes `RULES_CORPUS_COMMITMENT_PRESENT`
* feature:Config: `getCertcryptConfig`, the only exported profile; test profiles stay in the unpublished harness, and the CLI accepts a caller-supplied profile only through the test-only `--test-config` flag; `VerifierResult.production_verification` reports which regime produced a result
* feature:Conformance: the 160 fixtures of `certcrypt-conformance` `1.0.0` run via `npm run test:conformance`, compared with exact equality of `result_code`, `verification_target`, the set of `failed_check_ids` and every further member a fixture declares, gating publication through `prepublishOnly`; `CONFORMANCE_VECTORS_VERSION` is `null` on a build that did not run them, so a report can only name a contract that was actually verified
* feature:Packaging: ESM-only, Node >= 20, `exports` blocking deep imports into `dist/` so a signature component cannot be reached around `verifyComposite`
